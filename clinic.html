        What I do

        I compress the method spine of the earlier lessons (ask, orient, find the unit, budget it, check the population, name the gap, working or waiting, change one input, cross-check, conclude with limits) into six moves with the terminal command for each. In Perfetto or DevTools the same move is in brackets.

        1. Inventory. q.mjs ID threads [the process list]. Backend process? Worker? Netem lane? Window length?
        2. The complaint as a number (the table in step 1). Write it down with its lane.
        3. Frames over time. q.mjs ID frames [Perfetto: the PipelineReporter track of the Renderer; DevTools shows only part of it]. Find when things differ from a steady state. Read frames.mainFrameMs and frames.mainQueueMs; do not judge by colour.
        4. The main thread at that time. threads.mainUtilPct, main.longTasks, q.mjs ID tasks FROM TO 1 [the CrRendererMain track].
          • Long frame, no wait → busy. Go to 5a.
          • Short frame, long wait → held. Find what holds it: one long task (name it with q.mjs ID tree FROM TO), or a flood of short ones (count tasks per queue: taskQueues in summary). Then 5a for the holder.
          • Thread mostly idle → waiting. Go to 5b.
        5. Name the unit and its cost.
          1. If working: by category (main.scriptMs, styleMs, layoutMs, paintMs, gcMs; counts of layouts and forced layouts), then by function (q.mjs ID prof FROM TO [the flame chart; Bottom-Up]), then by unit: is this cost paid per frame, per scroll event, per message, per request, per cell?           2. If waiting: for what? A reply (ws.roundTrip split into upMs, serverWait, serverService, downMs; the backend's query #n spans and rows queue counter). Raster (raster.ms; commit → ActivateSyncTree on the compositor thread; the "presented-after" column of frames). The next vsync (a few to 17 ms, normal). A timer or an animation frame.         Question I holdTen questions, one or two per module. Answer each in a sentence or two before opening it.

        1 · First minute

        A trace arrives with the sentence "typing in the filter box is laggy". Which number do you write down first, and which three readings tell you where to look next?

        Answer

        Key press → first presented frame that shows the typed character (and, separately, → filtered rows on screen: two observation points). Then main-frame duration, the frame's queue wait, and main-thread utilisation with the longest task: long frame and no wait means the frame's own work; short frame and long wait means the thread is held; idle means waiting elsewhere (steps 1 and 2).

        2 · Frame colours

        Half the vsyncs of a scroll are "presented without the main update". Name two readings that would make this harmless and one that would make it a problem.

        Answer

        Harmless: main frames of a millisecond or two with no queue wait, in a compositor-animated scroll or separate wheel notches (the BeginMainFrame is sent before the draw); or a page whose content simply changes on few frames. A problem: main frames longer than an interval, or a queue wait near the frame's whole duration. The colour says where to look, not that anything is late (Module 2; step 2).

        3 · Two tables, one library

        Two pages use regular-table on the same data. One runs about eighteen layouts per scroll event, the other one per frame. What differs in what the library knows, and which read causes the extra layouts?

        Answer

        Column widths. With widths cached the draw is planned without reading layout and committed in an animation frame; with the cache emptied (resetAutoSize() per scroll) each drawn column is measured with th.offsetWidth inside the draw loop, and each read forces a layout of what was just written (Modules 3 and 5; case 5).

        4 · A forced layout

        A flame chart shows a Layout under a scroll listener. When is that an extra cost and when not? Which count decides?

        Answer

        Not extra when it is the frame's one layout done early (a read before any write, as with two virtualizers on one scroller): the lifecycle then has nothing left to lay out. Extra when writes follow the read and force another layout. Layouts per frame, against a control, decides (Module 5; field guide rows 6 and 7).

        5 · The backend's number

        Service time is 25 ms and constant. Users wait 700 ms. Give the arithmetic that makes both true, and the cheapest change on the client.

        Answer

        Requests arrive faster than one server completes them: at 60 a second against 40, ρ = 1.5, and after t seconds of overload the wait is about t × (ρ − 1): 1.45 s × 0.5 ≈ 0.73 s. The cheapest change is one request in flight with only the newest wanted range remembered, which ties the arrival rate to the service rate (Module 6; case 2).

        6 · Three paces

        Messages arrive at 9,000 a second, the display shows 60 frames a second, and the page draws per message. Which two buffers separate the three paces in a design that keeps up, and what does each hold?

        Answer

        A queue of messages before the handler (bounded by making the handler cheap: parse and store only), and a table of latest values per cell before the frame (which conflates by construction: a cell overwritten twice between frames is drawn once). The draw is then per frame, whatever the message rate (Module 7; case 3).

        7 · A stall

        The network delivers nothing for 1.3 s and then everything. State the age of the oldest value at that moment, and the property of the page that decides whether the burst is one dropped frame or a quarter of a second of them.

        Answer

        About 1.3 s: the stall's length. The property is whether the expensive step (the render or draw) runs once per message or is bounded per frame. A page that only schedules a render per message may coalesce a burst by accident; one that draws synchronously per message pays for each (Module 8; case 7).

        8 · Priorities

        Under a flood of WebSocket messages, why does a key press get a frame within milliseconds, the animation that follows it one frame per 100 ms, and a mouse drag a frame nearly every vsync?

        Answer

        Input tasks run at the highest priority; a discrete input makes the next BeginMainFrame highest too, once. After that the compositor queue is at normal priority behind the backlog and is lifted only by the 100 ms starvation rule. A gesture in progress keeps the use case, and with it the compositor queue's priority, at highest while input continues (Module 7; case 8).

        9 · A benchmark's number

        A library's benchmark prints 60 fps. Name three things you need to know before comparing it with anything.

        Answer

        Its clock (what increments the counter: round trips, draw calls, rAF callbacks, presented frames), its driver (real input or a script writing scrollTop, and when in the frame), and the contents of one unit (was the right content on screen at the presentation point). Module 10 found 60 fps reported for a list that was empty in 89 of 91 positions.

        10 · Another renderer

        You get a trace from a native renderer: spans with CPU time, a frame id, a few counters. A span render is 14 ms long with 1.6 ms of CPU. What do you conclude, what do you not, and which case of this module is its analogue?

        Answer

        The thread was waiting for 12 ms inside render, not working: optimizing its code cannot shorten it. Not concluded: what it waited for (GPU work, a present deadline, another client of the GPU) until a counter or the driver's accounting says. The analogue is case 6: a short main-thread frame whose content waits for raster. "Working or waiting" is the question that needs no browser (steps 18 and 19).

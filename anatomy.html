        Table engines under load · Module 3 · recorded 2026-11-16

        Three virtualizers take the same scroll. What does each one own, and what does that make it do under load?

        One wheel gesture scrolls a table of 100,000 rows. TanStack Virtual, regular-table and Perspective (which puts an engine behind regular-table) all keep a few dozen rows in the DOM, yet they divide the work differently: who creates the elements, who asks for data, when your code runs relative to the scroll event, how many draws may be in flight, and what stays on screen while an answer is late. This module reads each mechanism in the library's source and then finds it firing in a trace: a function name in the sampled profile, a count that matches, a layout where the source says there has to be one.

        At the end you should be able to say from memory what each design owns, and to predict from that, before opening a trace, what it will do under a given load. The last step tests exactly this with five loads.

        Why this matters for Tablelab. Tablelab's DOM frontend is regular-table today, with a Rust engine behind a socket: the shape of Perspective. Every row of the table at the end of this page (who owns the DOM, one pull in flight, what is rewritten per step, what the screen shows while late, how far the scrollbar reaches) is a decision the view core and its painters make again. Two finished designs, read down to "which line reads layout", show the consequences before we build them.

Tablelab's earlier note What a virtualizer owns (notes/virtualization.html) names the four jobs used in step 1. Style, layout and forced layout as such belong to Module 5; frames to Module 2.

        Knowledge I am using
        Visible range
        The first and last row that overlap the viewport. It changes when a row boundary crosses the top edge or the bottom edge.
        Notification rate
        How often the library tells you something changed. It bounds how often you render, not how much each render does.
        Hard learning

        I computed the notification rate from the row height alone: 9.7 px per frame against 24 px rows, so 40% of frames. The trace showed about 76%.         Overscan

The sizer you size to 48,000,000 px is laid out about 33,554,000 px tall by the browser, so End stops near row 1,398,000 and the rest cannot be reached by scrolling. regular-table: nothing per row at mount; a panel capped at 10,000,000 px and a proportional map, so End is the last row and one pixel is 0.2 rows. Traces: a-big-tanstack, a-big-regular (steps 5 and 13).

        6. Without scrolling back: name the two pipelines of regular-table, what selects each, and one way to tell them apart in a trace.

        Answer

        The plan-then-commit path (predraw, await data, await a frame, draw_sync) runs for a scroll when the row height and the needed column widths are cached. The asynchronous path (internal_draw → table_model.draw) runs for every draw() call and for a scroll that finds a size missing. In a trace: the first writes under Animation frame fired with one unforced layout after it; the second writes under Run microtasks inside the scroll event or the calling task, has no animation-frame callback, and shows forced layouts under internal_draw and _render_pass (steps 8 and 9).

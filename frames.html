        Table engines under load · Module 2 · recorded 2026-11-16

        Sixty times a second the display asks for a picture. What did the user get each time, and how do I know?

        Module 1 followed one scroll through the main thread: event, JavaScript, style, layout, paint, commit. This module stands on the other side of that commit, on the compositor thread, which answers every vsync whether the main thread is ready or not. We take one vsync apart event by event, then use the compositor's own record of each frame to say exactly what was shown: the main thread's update, an older one, or nothing.

        The module's centre is a contrast. The same table code is scrolled three ways: by a steady wheel gesture, by a scrollbar click that the compositor animates, and by single wheel notches. Chrome labels almost every frame of the first "presented", almost every frame of the second "presented without the main thread's update" and half the frames of the third, with a main thread that needs one or two milliseconds per frame in all of them; and in all three the rows reach the screen one vsync after the position they belong to. Working out why makes the words exact, and they are the words every later module reports: frames with the main thread's update, without it, dropped.

        Why this matters for Tablelab. Our goal names four observation points that must not be confused: DOM written, requestAnimationFrame, commit, presented. This module pins each to a trace event and measures the gaps between them. It also measures what a late draw costs in whole vsyncs, which is the budget our view core and painters have to share.

        What you need. Module 1 (Where does a scroll go?) for the trace vocabulary and the order of work inside one main frame. Each step links the trace it reads; every command shown was run on these traces. From the repository root: node lab/harness/q.mjs <id> frames prints one line per vsync.

        Knowledge I am using
        Vsync, BeginFrame
        The display refreshes at a fixed rate (60 Hz here: every 16.67 ms). Viz turns each refresh into a BeginFrame message to every compositor that asked for one. "A vsync" in this module means one such tick, identified by its sequence number.
        Three compositing actors
        CrRendererMain makes content (DOM, style, layout, paint). The renderer's Compositor thread owns the layers, scrolls and animates them and builds a frame per vsync. VizCompositorThread in the GPU process puts all processes' frames on the screen.
        Deadline
        Inside one vsync the compositor waits until a chosen moment, then draws with what it has. Which moment, and what it waits for, is this module's main mechanism (steps 7 to 9).

        Knowledge I am using
        BeginMainFrame
        The compositor's request to the main thread: "produce a frame for this vsync". It runs as one main-thread task and ends with a commit (or an abort when nothing changed).
        Pending and active tree
        The compositor keeps two copies of the layer tree. Commits go to the pending one, so the active one can keep being drawn and scrolled while new tiles are rastered.
        One draw per vsync
        A compositor frame is produced at most once per tick, at the deadline. What misses it waits for the next tick.

        No: that every frame works this way. Step 3 shows a frame where the compositor waits for the main thread; step 7 a scroll where the request leaves before the draw.

        Hard learning

        I believed that a main thread which finishes in 1 ms gets its rows into the current frame, and that "one frame late" was a symptom of slowness.         Knowledge I am using
        Four deadline modes
        IMMEDIATE: draw now. WAIT_FOR_SCROLL: draw after a third of the interval (step 7). REGULAR: the compositor has something to draw but a commit is expected: wait until shortly before the next tick (step 12). LATE: nothing to draw but the commit: wait until the next tick.

        Knowledge I am using
        Why a measure costs anything
        Each call creates a PerformanceMeasure entry, serializes its detail, stores it in the page's performance timeline and, with tracing on, writes a begin and an end event (Module 1, step 4, reads that code). None of it is free, and all of it runs on the thread being measured.
        Three estimates, three answers
        Sampling attributes whole sample intervals (about 0.15 ms here) to whatever function a sample lands in, which flatters nothing and can inflate short native calls. Subtraction of two runs includes the difference between the runs. A control quantity measured in the same run removes most of that difference.         1 · Order

        A wheel scroll, healthy. Put in order for one vsync N: DrawFrame, SendBeginMainFrame, Scheduler::BeginImplFrame, ActivateLayerTree, Commit, HandleGestureScrollUpdate. In which vsync's frame do the rows of that commit appear?

        Answer

        Scheduler::BeginImplFrame → HandleGestureScrollUpdate → DrawFrame → SendBeginMainFrame → Commit → ActivateLayerTree. The compositor draws before it asks. The rows appear in the frame of vsync N+1, about 17 ms after tick N (steps 1 and 2).

        2 · Two colours

        Two traces of the same table. In one almost every vsync is "presented", in the other almost every vsync is "presented without the pending main update". Main frames take 1 ms in both. Name one cause, and the event that would confirm it.

        Answer

        The driver of the scroll differs. In the second the BeginMainFrame is sent before the draw in each vsync: a compositor-animated scroll (deadline mode WAIT_FOR_SCROLL, on_critical_path: true) or separate wheel notches. Confirm with Scheduler::ScheduleBeginImplFrameDeadline's deadline mode and the order of SendBeginMainFrame and DrawFrame (steps 7 and 8).

        3 · A clean Frames track

        A colleague shows DevTools' Frames track with no dropped and no partially presented frames during a scroll, and concludes that the table kept up. What do you ask for?

        Answer

        The PipelineReporter states, and how long the main reporters lived. DevTools marks only frames with a DroppedFrame event, which Chromium writes only when a tracked smooth effect (a rAF loop, a main-thread animation, the scrolling thread itself) missed its update. A table that renders in a scroll handler can be hundreds of milliseconds behind with no mark (step 6).

        4 · Budget

        A draw takes 12 ms; an optimization brings it to 6 ms. Under a wheel scroll, how much sooner are the rows on screen? A regression takes it to 18 ms. How much later?

        Answer

        No sooner: both are presented with the next vsync; 6 ms buys slack. At 18 ms the frame misses the next draw: rows arrive one whole interval later (about 34 ms after their tick instead of 17) and are updated at 30 Hz, with the main thread idle for most of the second interval (steps 10 and 11).

        5 · Busy or slow

        A main reporter's SendBeginMainFrameToCommit stage is 200 ms long. Which single number tells you whether the frame was slow or the main thread was busy with something else?

        Answer

        begin_main_sent_to_started_us in that stage's breakdown (the lab's frames.mainQueueMs): the time the BeginMainFrame task waited in the queue. 199.6 of 201 ms in the long-task trace; under 0.1 ms in the slow-cell traces (step 12).

        6 · Observation points

        "The update is applied 0.5 ms after the server sends it." "The update is visible 1.7 ms after the server sends it." Both are from one trace. Which events end each interval, and which would you report for a table under scroll?

        Answer

        The first ends at the end of the DOM write (our app: tick apply measure); the second at presentation (Display::FrameDisplayed, or the end of the PipelineReporter that carries the commit). Report the second: during frame production the two are up to a full interval apart even when the main thread is fast, and more when it is not (steps 13 and 14).

        7 · A small difference

        Variant B shows 8% less layout time than variant A, one traced run each. What do you do before believing it?

        Answer

        Check that the two traces really differ in the intended input and were recorded with the same categories; repeat each at least five times; compare medians and ranges; and divide layout by a phase from the same run that the change should not affect. Identical runs here differ by up to 25% in time totals; counts (layouts, dirty objects, frames) are the numbers a single run can support (steps 15 to 17).

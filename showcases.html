        Table engines under load · Module 10 · recorded 2026-11-16

        A library shows off a demo and prints a frame rate. What did it measure?

        regular-table ships an example with two billion rows and a benchmark that prints "Throughput (fps)". TanStack Virtual ships a fixed list, a measured list, a 50,000-row table and a benchmark that reports "60 fps, 0 long frames". This module runs those pages as shipped, at pinned revisions, under the same instruments as the rest of the course, and reads each example's code next to its trace.

        For every showcase the steps answer the same things: what the code sets up, what one unit of work is, where the time goes, what a user would have seen, and what the showcase does not exercise. Three of the benchmark numbers turn out to count something other than frames on a screen. One of them reports a perfect score while the list is blank.

        Why this matters for Tablelab. We will publish numbers for our own engine and compare them with these libraries. A number is only comparable if we know which clock counted it and what was on the screen while it ticked. The study plan asks us to name observation points precisely (DOM completion ≠ rAF ≠ commit ≠ presentation); these traces show what happens when a benchmark does not.

        What you need. Module 1 (Where does a scroll go?) for the trace vocabulary and Module 2 (What happened to each frame?) for frame outcomes. Module 3 reads both libraries' source in depth; this module quotes only the lines each trace needs. Perspective's own examples are traced in Module 9.

        Next question → A wheel step moved the content 39 px and the table laid out 2,120 objects. Why is everything dirty?

        Question I holdWhy does a small scroll step rewrite and re-lay-out every cell of this table?

        Predict first

        Rows are 19 px high. In the frame of step 2 the wheel moved the scroll position by 39 px. By how many rows did the table move?

        About 7,800. Two billion rows of 19 px would need a 38-billion-pixel scroller. regular-table caps the scroller at 10,000,000 px and maps the scroll position to rows by proportion, so one pixel is about 200 rows.

        What I see

        At about 200 rows per pixel, a mouse step of 110,420 px is about 22 million rows, and one pixel of thumb travel is about 2.4 million rows (110,420 ÷ 9.3 × 200). No scroll position reachable by wheel, key or thumb is one row away from another.

        So on every frame every cell shows a different value. Three things follow, each visible in the trace:

        Every text changes. The main thread shaped text 123,805 times during the scroll of step 2 (InlineNode::ShapeTextIncludingFirstLine), about 1,040 per frame. regular-table writes a cell's text only if it differs from the last value; here it always differs.

        Every element is restyled. elements over style recalculations. The library writes four CSS custom properties on the <table> at every commit, and custom properties inherit.

        The whole table is laid out. dirty objects over layouts. Column widths of an automatic-layout table depend on cell content.

        Forced layout
        Layout that JavaScript makes the browser run at once, by reading a geometry property after changing the DOM. One per frame replaces the layout the frame would have run anyway. Several per frame, each after new writes, is thrashing (Module 5).
        Two draw paths

        Hard learning

        Next question → Driven exactly this way, one protocol call per iteration: what runs between two calls?

        Question I holdWhat is inside one iteration, and what is between two?

        What I do

        The scenario u-rt-bench-steps sends sixty page.evaluate calls, as the runner does. I wrapped each in one performance.measure, app: bench step, from the call to the resolved draw, so the iterations show as bars. The runner has no such measure.

        1. 1One iteration, 1.9 ms: the task that runs the protocol call. It contains the data listener, regular-table's cell writes and the style listener, all in microtasks. No style, no layout, no paint.
        2. 2The next task is not the next iteration. It is a BeginMainFrame that the compositor had queued, 14.5 ms.
        3. 3In it: style for 1,147 elements and layout of 2,147 objects, for the cells the iteration wrote.
        4. 4Then the scroll event that the scrollTop write had queued, and regular-table's ordinary scroll path draws the table again in requestAnimationFrame (draw_sync and the style listener are sampled here).
        5. 5A second style recalculation: 459 elements whose classes the style listener removed and added back. No text changed (2 layout objects).
        6. 6Paint and commit.
        7. 7Only now the next protocol call gets the main thread.
        What I see

        iterations with a median of each, and main frames with a median of between them. The sixty calls started within 881 ms, about 67 a second. Six of them ran 3 ms after the one before, with no frame in between.

        What I think

        The iteration itself is JavaScript only. The rendering it causes runs in a different task, and that task delays the next iteration's protocol call. So the runner's clock does include most of the frame's cost, by queueing, but it does not wait for it: when two calls arrive before the next refresh, the second runs at once. "Throughput (fps)" can therefore exceed the display's refresh rate, as it does here (67 against 60).

        Each iteration also draws the table twice. I read the reason in source but did not prove it by experiment: the awaiting draw and the scroll path compute the last visible column differently (scroll_panel.ts:810 against 245–248), and a different last column invalidates the window (655–659).

        Hard learning

        The frames lane of this trace is amber: refreshes "presented without the main thread's update". I read that as fifty-three frames with stale rows. The frame records say something narrower. Each refresh has two: a compositor-only record presented about 7 ms after its vsync, and the main thread's record for the same refresh, presented about 24 ms after it. The first carries the previous refresh's table. So every refresh showed a new table, one refresh late. The rule I keep: "without the main update" means the update for that vsync missed it; look at the main frame's own presentation time before calling a frame stale (Module 2).

        DOM completion is not a frame
        The promise of draw() resolves when the cells are in the DOM. Style, layout, paint, raster and presentation happen later, in tasks that need the main thread back.
        Scroll events coalesce
        A scroll event reports that the position changed since the last frame, not each write. Sixty writes in one task give one event: in this trace.
        Dropped, but not shown as dropped
        The compositor's records mark refreshes dropped. DevTools' Frames track would show , because no scroll or animation was running on the compositor that could be judged unsmooth (Module 2).

That last sentence is an inference: I traced TanStack's example, not the benchmark's pages.

        One more claim in that README does not match the pinned source. It explains a slow mount at 100,000 rows by "we eagerly populate measurementsCache (one object per item)". At 3.19.11 single-lane lists keep sizes in a Float64Array and create item objects lazily; Module 3 reads that code.

        Hard learning

        I believed that a steady 60 from a rAF counter, with the compositor's frame records all green, meant a smooth scroll. Both instruments were right and the list was blank. A frame rate measures that frames were made on time. It does not measure that the frame showed the right thing. The rule I keep: a scroll benchmark needs a content check, at the moment of paint, next to its frame count.

        For a table engine

        Proposal: Tablelab's scroll benchmark records, per presented frame, whether the rows in the frame match the scroll position (the lab's "content complete" mark is this check) and how old the data is, and drives the scroll with input events so that the compositor and the frontend are in their real order. A frame count alone would have passed this run.

        What I think

        1. Which clock ticked? Protocol round trips, a library's draw counter, rAF callbacks and presented frames are four different counts. Only the last is about the screen, and steps 6 to 8 and 14 show each of the others reading "about 60" for a different reason.

        2. Who moved the scroller, and when in the frame? An input goes to the compositor first and reaches the page as a scroll event at the start of a frame. A script write goes to the main thread only, and if it is made in a rAF callback the page hears of it a frame later. Same pixels of travel, different pipeline.

        3. What did one unit contain? JavaScript only (an awaited draw), or style and layout too (if something forced them, or a frame ran), or paint and raster (only if a frame was produced). Step 7's two bars are the same sixty iterations with and without the last two.

        4. What was on the screen? A frame can be on time and wrong: blank (step 14), one refresh behind (steps 6 and 13), or stale. A benchmark has to look.

        5. What workload was it? Cells on screen, what a step changes, where the data is. The showcases differ by a hundred times in cells, and each is the favourable case for its library's design: regular-table's shows a full rewrite fitting in a frame, TanStack's show a small window with almost nothing in it.

        For a table engine

        Proposal for Tablelab's published numbers: drive with input events through the browser; report the compositor's frame outcomes and the main thread's presentation delay rather than a mean rate; mark content-complete per frame and report data age; state cells on screen and cells changed per step; and keep one run that is deliberately unfavourable (a full rewrite, a wide viewport, a slow source) next to the favourable one.

        Question I holdWhat should I now be able to say without looking?

        1regular-table's benchmark prints "Throughput (fps)". What event increments it, and why can it be higher than the display's refresh rate?
        Answer

        One returned page.evaluate call (benchmark.mjs:125–129, 166). The call resolves when the awaited draw() has written the DOM; nothing waits for a frame. When two calls reach the main thread within one refresh the second runs at once: 60 calls in 881 ms in u-rt-bench-steps.

        2The same sixty iterations cost about the same layout time as one loop and as sixty protocol calls, but paint almost vanishes in the loop. Why?
        Answer

        In the loop, the read in scrollTop += 100 forces style and layout for the previous draw, so that work happens anyway. Paint happens only in a frame, and the loop never yields for one: one task, one frame. With protocol calls a BeginMainFrame runs between most iterations.

        3In two_billion_rows, why does a 39 px wheel step change every cell, and what three costs follow?
        Answer

        The scroller is capped at 10,000,000 px and position maps to rows by proportion, about 200 rows per pixel. So every text changes (a thousand text shapings per frame), the four custom properties written on the table restyle every element, and the automatic table layout runs over the whole table.

        4A trace shows 127 forced layouts in a two-second scroll. What do you check before calling it thrashing?
        Answer

        Layouts per frame and the frame's length, against a run without them. In the diagonal scroll each forced layout replaced the frame's own layout; the median frame was about a millisecond longer.

        5TanStack's table example uses overscan: 20. What does that change about renders per scroll event, and why?
        Answer

        Nothing about how often: the notification is keyed on the first and last visible index (virtual-core index.ts:1021–1024). It changes how many rows each render produces: about 58 instead of about 20.

        6A scroll benchmark writes scrollTop in a rAF callback and reports 60 fps with no long frame; the compositor's records are all "presented with the main update". Name the thing neither measured, and the mechanism that hid it.
        Answer

        Whether the frame contained rows. The scroll event for a write made in a rAF callback fires in the next frame, so the library renders for a position the driver has already left. At thousands of pixels per frame, those rows are off screen: an empty list, on time, sixty times a second.

        7Two traces: one has 2 frames "without the main update", the other 82. In which did rows reach the screen later after their scroll position?
        Answer

        Neither: one refresh in both (u-tv-fixed-rows and u-tv-dynamic-scrollup). The count follows how often the main thread had an update and whether the compositor asked before or after drawing. Compare presentation delay, not the colour count.

        Table engines under load · Module 4 · recorded 2026-11-16

        A table scrolls. How much JavaScript runs in each frame, and what does that amount grow with?

        The same wheel scroll goes through three table designs: a keyed row pool on TanStack Virtual, regular-table, and React on the same range math. Each runs JavaScript in every frame, but not the same amount, and not for the same reason: one does work for the rows that enter, one for every cell on screen, one renders every row and writes almost none. This module measures that work, changes one input at a time (cells, speed, formatting, memoization, allocation, warm-up), and reads each result three ways: counters, spans and the sampled profile.

        At the end you should be able to look at a table design and say what its per-frame JavaScript scales with, find the function that owns the time in a sampled profile and say what the sampler can and cannot tell you, recognize garbage collection and JIT warm-up in a trace, and judge an abstraction by what it adds per frame.

        Why this matters for Tablelab. The study plan asks where the DOM rendering cost is and what should cross to the renderer. The JavaScript share of that cost is set by a design decision made before any code is optimized: whether a scroll step's work is proportional to the cells that changed or to the cells that are visible. The traces here put numbers on both, and on what formatting, an abstraction layer, allocation and cold code add on top.

        What you need. Module 1 (Where does a scroll go?) for the trace vocabulary, especially step 3 (JavaScript bars come from samples). Module 3 (Three designs read in source) explains who owns the DOM in each panel; this module only counts what that ownership costs. Frame outcomes belong to Module 2, style and layout to Module 5; they are linked where they appear and not re-taught.

        Three kinds of evidence. A counter is a number the page itself counted (cellsWritten, rowRenders): exact, and it survives a noisy run. A span is a named interval in the trace (EventDispatch, our app: draw measure): exact in time, only where someone instrumented. A sample is one look at the JavaScript stack about every 0.15 ms: it sees everything, statistically. Most steps use two of the three against each other.

        Knowledge I am using
        What a sample count means
        For timer samples: time on the stack ÷ interval, with random error. A function with 3 samples ran for something between almost nothing and about 1 ms. It says nothing about calls.
        Requested samples
        Samples taken because code asked (performance.mark, measure, each FunctionCall span, console.timeStamp). They are exact in time and not random, so they over-represent the place that asked.
        Negative timeDeltas
        Each delta is the difference to the previous sample in the file (profile-generator.cc:770–778). Out-of-order samples make it negative. Sort first.

        Question I holdGiven a table design, or a profile of one, can I say what its JavaScript scales with, what the evidence can carry, and what to change first?

        What I do

        Answer each question before opening it. The numbers that matter are orders of magnitude; the reasoning is what should come back.

        Questions
        1. A table keeps one element per visible row and creates and removes rows as they scroll in and out. What does its per-frame JavaScript scale with? What about one that rewrites the text of fixed cells? One that renders React rows without memo?

        Keyed: entering rows per frame (speed ÷ frame rate ÷ row height) × visible columns; independent of viewport height. Positional, such as regular-table: visible cells, independent of speed once a row changes per frame. React without memo: every visible row is rendered again (visible cells in the render phase), while the DOM writes are the keyed pool's. Steps 1, 4, 6.

        2. A profile's top JavaScript self time is a one-line function that reads el.scrollLeft. What do you do next, and what do you not conclude?

        Print the spans under a call of it (tree, or the DevTools flame chart): a Layout forced by the read is there. Self time includes native work with no name in the profile. Do not conclude the function is slow code, nor that removing the read saves its whole self time. Step 2.

        3. measure has 153 samples for 126 calls, formatCell 15 samples for 71,869 calls. Explain both, and say which numbers you would trust for each.

        performance.measure asks the profiler for a sample on every call, and requested samples are written out of time order; summing deltas in file order roughly doubles its apparent cost. Trust a marks-off control run. formatCell is too short to be caught by a 0.15 ms timer; trust the counter for the count and a measured span around the loop for the time. Step 3.

        4. At what scroll speed does a keyed pool stop being cheaper than a positional one, and why is there a crossover at all?

        When about three quarters of the viewport is replaced per frame (38,400 px/s here). A created-and-removed cell cost about 40% more JavaScript than a rewritten one, and remove() was the largest part; keyed wins below the crossover only because it touches far fewer cells. Steps 6 and 7.

        5. A slow scroll shows many frames "without main update" while the main thread is 90% idle. What happened, and what is worth checking in the table's draw?

        Each such frame follows a main frame that ended with NO_UPDATE: nothing changed between row crossings. Check whether those main frames did work anyway. regular-table ran a full draw of 3.6 ms in 41 of them, when only its last row index changed. Step 8.

        6. You must format 500 numeric cells per frame. What is the cost with a shared Intl.NumberFormat, and with toLocaleString("en-US", options)? Why are the second and new Intl.NumberFormat per cell the same?

        About 0.15 ms against about 5.5 ms per frame (0.3 and 11 µs per cell on this machine). V8 caches the formatter behind toLocaleString only when no options are passed; with options it constructs one per call. Step 9.

        7. Someone proposes React.memo on rows, and someone else a larger overscan, to make scrolling cheaper. What do the counters say, what do the clocks say, and what do you tell them about GC and the first scroll?

        memo: row renders fall about 19-fold (certain), time under flushSync by a fifth to a third, script total within noise; most of the layer's 0.5 to 0.8 ms per frame is fixed per render. Overscan does not reduce renders (notification is on the visible range) and makes each larger. GC: scavenges of 0.2 to 0.8 ms and major pauses of 1 to 3 ms cost no frame here because the live heap is tiny; creating garbage costs more than collecting it, and DOM writes are garbage too. First scroll: several times slower for a few frames in React; compilation runs on pool threads and new code arrives at frame boundaries. Steps 11 to 15.

        May conclude

        Yes, from this module: each design's cost model in cells per frame; how to read a sampled profile against counters and spans; what GC and tier-up look like in a trace and what they cost at this scale.

        No: a ranking of libraries, or numbers for another machine. One run per scenario, headless, tracing on, a table of plain text cells. The method transfers; the microseconds do not.

        For a table engine

        Carried to Tablelab as proposals: (1) choose the painter's unit deliberately (cells that changed, not cells that are visible) and let the view core supply the difference; (2) keep counters in the painter and report them with every timing; (3) format on the engine side or with per-column shared formatters; (4) keep data off the renderer's main thread so collector pauses stay small; (5) give the first interaction after load its own measurement.

        • A design's per-frame JavaScript = fixed part + unit cost × units; the designs here differ mainly in the unit (entering rows, visible cells, rendered rows), less in the unit cost (about 1 to 2 µs per cell).

Table engines under load a traced course · TanStack Virtual, regular-table, Perspective · Chrome 154 Repository

Tablelab studies · recorded 2026-11-16

A table scrolls, updates arrive, the network misbehaves. What runs, on which thread, and which frames does the user get?

Eleven modules, each a chain of questions answered from real Chrome traces of three table implementations and checked against the source of the libraries and of Chromium. Every trace is in this repository: open it in Perfetto or DevTools next to the page and look for yourself.

The subjects are TanStack Virtual (the library computes which rows are visible; your code owns the DOM), regular-table (the library owns a <table> and asks you for a rectangle of data), and Perspective (a query engine in a worker or on a server, drawing through regular-table). They are good implementations that made different choices, which is what makes them worth tracing side by side. The frame of every module is the same: a case you can run, a prediction, the trace, the source that explains it, what may be concluded, and what the trace taught that I did not expect.

The method every module uses

It is the method of the two earlier lessons (Where does a scroll go? and Tablelab's notes/trace-reading.html), applied to harder cases. A trace has no beginning and no point; a question gives it both.

AskOne question, written down, with the number that would count as an answer.
PredictCommit to an expectation before looking. A wrong prediction is the most useful thing a step can produce.
OrientWhat did this trace record: which processes, threads, categories? What can it not show?
Find the unitOne repetition of the work: a frame, a draw, a message, a request.
Budget itAccount for the whole period. What is left over is a part you have not named.
Check the populationCounts, median, tail, worst case. Is the unit you looked at typical?
Working or waiting?Elapsed time against work done. A long bar can be a queue.
Change one inputA control and a treatment that differ in one thing.
Cross-checkDoes the source say the same? Does a second trace?
ConcludeClaim, evidence, limit. Each limit is a candidate next question.

Each step tags what it establishes as read in source, measured, inferred or rejected, and the side rail collects them as you go. Steps marked Hard learning record a belief the trace contradicted.

Yardsticks

16.7 msOne frame at 60 Hz, the rate these traces were recorded at. At 120 Hz it is 8.3 ms. The main thread does not get all of it: the compositor draws at a deadline inside the interval (Module 2).
50 msThe length at which a task is called long: input that arrives during it waits for it.
100 msHow long Chrome's main-thread scheduler lets rendering starve before it raises the priority of the next frame (Module 7).
ρ = arrival rate × service timeUtilisation of anything that serves one thing at a time: a main thread applying messages, a backend running queries. Above 1 the queue grows without bound, however fast each item is (Modules 6–8).
Data ageNow minus the time the value was produced, measured where the user sees it. Throughput can look fine while age grows.

Opening the traces

Every trace is a gzipped Chrome JSON trace in traces/, recorded with the categories DevTools uses plus the compositor's, the scheduler's and V8's sampler. Where the scenario has a backend, the backend's own spans are in the same file as a process named Backend (node), on the same clock.

  • Perfetto (every process and thread, SQL): each step has an "open in Perfetto" link, which loads the file from this repository. Or drag a downloaded file onto ui.perfetto.dev. Press W/S to zoom, A/D to pan; type : for a SQL prompt.
  • Chrome DevTools (the JavaScript flame chart, frames track, friendly names): Performance panel → Load profile → the downloaded .json.gz. Turn off Settings → Ignore list to see library frames by name.
  • The terminal: node lab/harness/q.mjs <id> summary | frames | tree | prof | tasks | slices … prints what the charts in these pages are drawn from, on the same time axis.

To run a case yourself and record your own trace: cd lab && npm ci && npm run build && npm run serve, open the printed address, and use the query string shown under each trace link. README has the details and the limits of these recordings.

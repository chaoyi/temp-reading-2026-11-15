        Table engines under load · Module 9 · recorded 2026-11-16

        A real product built on regular-table: what do one scroll and one update cost through every layer of Perspective?

        Perspective 5.9.2 shows a table through regular-table, and keeps the data in a query engine that lives somewhere else: in a Web Worker of the same page, or in a Node process behind a WebSocket. This module follows one scroll and one table.update() through all five layers, counts the requests each draw sends, finds what decides how often the grid redraws, and then moves the engine 100 ms away.

        Why this matters for Tablelab. Tablelab has the same shape: an engine behind a transport, a window that the page pulls, change notifications that the engine pushes, and regular-table to draw. Perspective has already made each of those choices in shipped code. The traces show what each choice costs when it is cheap (a worker 0.05 ms away) and when it is not (a server 100 ms away), so we can keep the good ones and avoid three that the traces show to be expensive.

This module leans on, and does not repeat, Module 3 (regular-table's draw loop in source), Module 6 (request policies), Module 7 (the three paces and conflation) and Module 8 (delay).         Knowledge I am using
        Request and response
        Every call to the engine is a protobuf Request { msg_id, entity_id, one of ~40 request kinds }; the answer is a Response with the same msg_id (perspective.proto:116–213). A round trip is one request and its answer.
        One-shot and subscription
        Most calls resolve once. view.on_update registers a callback that the engine may answer many times with the same id: the push channel.
        Dedicated worker

        What a minified or WebAssembly frame still gives
        Its duration and its place in the order. Most of this module is counting messages and reading their order, which does not need names.

        Question I holdA steady wheel scroll moves the table 40 px per frame. For one frame: who asks for rows, who answers, and in which frame are those rows written?

        Predict first

        The engine sits in a worker and answers a window request in about 0.15 ms. A scroll event is dispatched at the start of frame N. The rows for that scroll position are written to the DOM…

        What I think

        This is a pipeline with a depth of one frame, built from two reasonable rules: fetch asynchronously, and write the DOM only in requestAnimationFrame.         Knowledge I am using
        Order inside a main frame
        Input and scroll events, then animation callbacks, then style, layout, paint, commit, as one task (Module 1, step 8). A message that arrives during that task runs after it.
        Pipeline depth
        How many frames pass between the input a draw answers and the frame that shows it. Depth one means the content is always one frame of scrolling behind; nothing is blank, because regular-table's table is sticky and keeps showing the previous rows.
        Work or waiting
        Of the 15.8 ms from request to DOM, about 1 ms is work on either thread. A faster engine cannot shorten the rest.

        Latest wins, one in flight

        4 · Pacing

        What decides how often Perspective redraws under a steady stream of updates? Give the two mechanisms and what each one limits.

        Answer

        A draw lock that allows one running and one parked draw (limits overlap, conflates only when notifications outrun draws), and a sleep before each update draw equal to the mean wall-clock time of the last five draws (limits duty cycle to about half).         About 420 ms of throttle sleep (the mean of the last five draw times), then 4 serial round trips of 100 ms (schema, row count, dimension probe, window), then about 1 ms of work. With setThrottle(0) the period was 407 ms.

        Table engines under load · Module 7 · recorded 2026-11-16

        The server pushes 8,000 cell updates a second. How many should the page apply, when, and how old is a value when you see it?

        A table is open and a server pushes new cell values over a WebSocket on its own clock. Three things now run at three speeds: the server produces at its rate, the page applies at another, and the display shows a picture 60 times a second. This module follows one update from the server's timer to a pixel, then raises the rate until the page can no longer keep up, and compares what six policies do about it.

        Afterwards you can reason about any live table as three paces and the two buffers between them; find the knee, the rate at which applying per message stops keeping up, and recognise it in a trace; measure data age at three points (handled, in the DOM, on screen); and say what Chrome's main-thread scheduler does when messages flood the thread.

        Why this matters for Tablelab. This is the Stage 0b / Pass 1 question: ingestion, publication and rendering as decoupled paces, with conflation and one pull in flight between them, and the difference between coalescing notifications and conflating data. Every design choice in that sentence appears below as a recorded trace with a control next to it.

        Question I holdBefore any load: one value leaves the server. Which threads touch it, in what order, and where does its time go before I can see it?

        Predict first

        The server sends one cell value 60 times a second. A value crosses three processes (the Node backend, Chrome's network service, the renderer), runs our handler, and is written into one cell. It will turn out to be about 9 ms old when it reaches the screen. Where is most of that time spent?

        What I see

        Three paces. The server produces when its timer says so. The page handles one message per task, as soon as the main thread is free. The display starts a frame every 16.67 ms. And two places where a value waits for the next pace:

        Buffer 1, between server and page: the kernel's socket buffers, the network service, a mojo pipe, and the main thread's task queue. It keeps every message, in order. It can only grow or drain.

        Buffer 2, between page and display: the DOM itself. It holds one value per cell; a newer value overwrites an older one that no frame has shown yet. The renderer reads it once per frame.

        What I think

        The two buffers have opposite characters. Buffer 1 is a queue: its length is how far the page is behind. Buffer 2 is a table of latest values: it has no length, only a freshness. Every policy in this module is a decision about which kind of buffer a value waits in, and where that buffer lives.

        A value is written into the DOM 0.3 ms after the server produced it and is on screen 9 ms after. Name the three paces involved and say where the 8.7 ms went.

        Answer

        2

        Two recordings of the same page differ by 16 ms in ageOnScreen at every percentile. What do you check before blaming the knob that differs?

        Answer

        "Presented-after" in q.mjs <id> frames. If one is near 1.5 ms and the other near 17 ms, the display compositor or the renderer's compositor is one frame behind in one of them: a self-sustaining state that lasts while every vsync carries a commit (step 3). Compare within a state, or compare age at the DOM.

        3

        At 4,000 messages a second the main thread is 66% busy and data age is flat. Estimate the knee. Then name three things you expect in a trace recorded at twice that rate.

        Answer

        4,000 ÷ 0.66 ≈ 6,000 a second (the measured capacity was a little higher, 6,700 to 7,200, and 5,400 in another recording). Past it: age at handling grows with slope 1 − μ/λ; the main frame's wait for the main thread grows with it, up to 100 ms; and work continues after the producer stops, for about as long as the last message was old (step 7).

        4

        regular-table drops draw requests that arrive while one draw runs and another waits. Why did 2,000 requests a second still produce 2,000 draws?

        Answer

        With a data listener that answers synchronously every await in draw() resolves in microtasks, so the draw is finished before its task ends. No request ever arrives while the lock is held. Coalescing needs a gap between request and work: a later task (React's scheduler), a frame (per-frame apply), or a slow data source (step 6, 9).

        5

        "Applying in requestAnimationFrame adds up to a frame of latency." True or false, and at which observation point?

        Answer

        True at the DOM (median 8.6 ms, worst 16.7 ms later), false on screen: a value written by a message task is shown by the next frame that starts after it, a value written in the callback by that same frame. Per value the on-screen ages were 9.9/17.5 and 10.0/17.5 ms (step 11).

        6

        The page is overloaded and nobody is touching it. A BeginMainFrame task is posted. On which queue, at which priority, and how long does it wait? What changes during a compositor-driven scroll?

        Answer

        On COMPOSITOR_TQ at normal priority, the same as the WebSocket message tasks on FRAME_LOADING_TQ, so first in, first out: it waits as long as the main thread's backlog, until 100 ms without a main frame raise the queue to very high priority (ten frames a second). During a compositor-driven scroll the queue is at low priority, so under a flood the frame gets only that 100 ms floor; the scroll itself stays smooth on the compositor (steps 15, 16).

        7

        Per-frame apply, a worker with a pull per frame, and server conflation all end up painting the same 24 cells 60 times a second. What distinguishes them, and what do all three lose?

        Answer

        How far a discarded update travels before it is overwritten: to the main thread's map (still one main-thread task per message), to a worker (main thread sees one batch per frame), or nowhere (four fifths never left the server, which also relieves the network). All three lose the values between two reads; acceptable for a display of current values, not for consumers that need every event (steps 10, 12, 13).

        Table engines under load · Module 5 · recorded 2026-11-16

        The JavaScript has finished. What does the browser still have to do, and what decides its price?

        A table's script writes text into cells, creates rows, sets a class. Everything after that is the browser's: recalculate style, lay out, pre-paint, paint, layerize, commit, raster on worker threads, activate, draw. In the large-table traces of this course that second half is two to four times the script time. This module reads it stage by stage, in the same scrolls recorded for three table designs, and ties each stage to a decision the table made.

        Why this matters for Tablelab. This is the "Pass 2" question of the study plan: which browser rendering work does the table require, and which can it avoid? The answers here are counts first (elements restyled, layout objects dirty, paint layers repainted, tiles rastered), because counts survive a faster machine and times do not.

        What you need. Module 1 (Where does a scroll go?) for the trace vocabulary; its steps 21, 25 and 26 introduced the non-composited scroller, the forced reflow and heavy paint at small scale, and this module builds on them. Frame outcomes (green, amber, red boxes) are Module 2's (frames.html); the libraries' draw pipelines are Module 3's (anatomy.html); script cost is Module 4's (javascript.html).

        Recorded 2026-11-16, headless Chrome 154.0.8037.57 (software raster and compositing, a synthetic 60 Hz vsync), device scale factor 1.75, one traced run per scenario unless a table says otherwise. A scroll scenario is a constant-speed wheel gesture that the harness plays twice back to back, so "the scroll" lasts about two seconds.         Three numbers in that list are not times. They are the trace telling me how much each stage was asked to do: 616 elements, 1123 of 1228 objects, 20 raster tasks. A time changes with the machine; these change only when the table does something else.

        Layout object

        Knowledge I am using
        Thrashing
        Write, read, write, read, where every write dirties layout: each read then pays a layout. The damage is the number of dirtying writes that are separated by reads, not the number of reads.
